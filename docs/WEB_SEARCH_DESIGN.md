# 联网功能 — 设计与影响评估

> 状态：**待实现**（设计讨论稿，尚未动工）
> 目的：在动手前过一遍流程，评估对现有架构的影响，列清需要拍板的决策。

---

## 背景

项目早期讨论过"DeepSeek 不联网"，当时决定**不做 RAG，只注入当前日期**。

现在有人想做"联网功能"。需要分清：**这不是 RAG**（不需要向量库、不需要离线知识库），而是**实时网络搜索注入**——比 RAG 轻得多。

---

## 一、联网功能本质

三步：

1. **判断要不要搜**——大多数情绪倾诉不需要（"我今天好累"），只有事实/时事类才需要（"最近 XX 发生了什么"）。
2. **搜一下**——调外部搜索 API，拿回 top 几条结果。
3. **注入 + 生成**——把结果塞进 prompt，让 LLM **用人格口吻**把信息说出来，而不是复述搜索结果。

---

## 二、插入现有链路的位置

当前链路：
```
用户输入 → safety层 → scene分类 → DeepSeek(流式) → 逐句TTS → SSE → 前端(逐字渐显 + 音频队列)
```

联网插在 **safety 之后、LLM 之前**：
```
用户输入
  → safety层                 ← 不变。命中危机 → 固定文案，绝不联网
  → 【新增】需要联网吗?
       否 → 走现有链路（绝大多数对话走这条）
       是 → 调搜索API → 结果注入 context → 进现有流式链路
  → scene分类
  → DeepSeek(流式) → 逐句TTS → 前端
```

### 关键设计原则：pre-LLM 注入，不要 tool-calling

搜索必须做在 LLM 调用**之前**（pre-LLM 注入），**不要**让 LLM 在生成中途调工具（tool-calling）。

原因：tool-calling 会**打断流式输出**，把现有的逐句 TTS + 逐字渐显全毁掉。pre-LLM 注入则让现有流式管线**一行都不用改**。

---

## 三、对现有功能的影响

| 现有功能 | 影响 | 说明 |
|---|---|---|
| 流式输出 / 逐句TTS / 逐字渐显 | ✅ 基本不受影响 | 搜索发生在 `stream_complete` 之前，流式管线不动 |
| 打断 / 手机音频 / 音频队列 | ✅ 不受影响 | 纯前端播放层；abort 照样能打断整个流 |
| 按人格 temperature / session 持久化 | ✅ 不受影响 | 正交功能 |
| **延迟 / 陪伴感** | ⚠️ 要注意 | 搜索加 1~3s，首句音频变慢。陪伴体靠"秒回"的在场感，所以**只在真需要时搜** |
| **safety 层** | ⚠️ 要改造 | 搜索结果是外部内容、**绕过了输入安全检查**。危机话题 + 联网更危险 |
| **人格一致性** | ⚠️ 要注意 | 直接塞结果，AI 易"出戏"变成搜索引擎、开始列点。需 prompt 约束 |
| scene 分类 | ⚠️ 多一道判断 | "要不要联网"是新增的 pre-LLM 决策 |
| 成本 | ⚠️ 小幅上升 | 每次搜索 = 搜索API调用 + 更大的 LLM 上下文。只在需要时触发，可控 |
| 降级链路 | ⚠️ 要新增 | 搜索API挂了要静默跳过、用 LLM 自身知识答。可照搬现有 `LLMError→mock` 降级模式 |
| **部署** | ⚠️ 老问题 | 改 `service.py`/`deepseek.py` 会撞上线上 admin 代码分叉，必须精准小改、不可整文件覆盖 |

## 四、本项目环境里的两个特别的坑

### 1. 服务器网络限制
线上阿里云 ECS **连 github / PyPI 都不通**。所以搜索 API **必须选国内可达的**（如博查 Bocha、Bing 国内端点、或自带代理的服务），不能想当然用 Google。
→ **动手前第一件事：在服务器上验证候选搜索 API 的连通性。** 这个不通，后面都是空谈。

### 2. "要不要联网"如何判断
三种方案，建议从便宜的开始：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 关键词启发式（最近/今天/新闻/天气/比分/股价…） | 零延迟、零成本 | 不够准 |
| 轻量 LLM 分类（仿现有 scene classifier） | 更准 | 多一次调用、加延迟 |
| DeepSeek tool-calling 自行决定 | 最"智能" | ❌ 打断流式，不采用 |

---

## 五、需要拍板的决策

1. **触发方式**：关键词启发式（推荐先用）还是 LLM 判断？
2. **搜索服务商**：哪个国内可达？（决定前先测服务器连通性）
3. **适用范围**：所有人格都联网，还是只在某些场景？（深夜情绪倾诉大概率不该联网）
4. **安全红线**：
   - 危机话题禁联网（必须有）
   - 搜索结果要不要二次过滤？

---

## 六、结论

- 架构上**对现有东西侵入很小**：流式 / 音频 / 打断 / 逐字渐显 / 按人格参数 全不动。
- 主要风险集中在 **延迟、safety、人格出戏** 三处——都是可控的产品 / prompt 问题，不是架构难题。
- **前置阻塞项**：先确认"服务器能连哪个搜索 API"，这是一切的前提。
